### 플러터에서 Next.js로 급선회한 이유

안녕하세요! 게임 홍보를 위한 저만의 아지트, 이 블로그를 구축 중인 개발자입니다. 첫 번째 포스트에서 말씀드렸듯, 저는 이 웹사이트를 직접 만들기로 결심했습니다. 자존심이 걸린 문제였거든요.

처음에는 제가 가장 자신 있고 좋아하는 기술인 **플러터(Flutter)** 로 블로그를 만들려고 했습니다. 플러터는 웹 빌드도 지원하니까요! 하지만, 곧바로 예상치 못한 거대한 문제에 부딪히게 됩니다.

### 용량 30MB의 충격과 공포

아주 간단한 한 페이지짜리 웹사이트를 플러터로 빌드했는데, 결과물의 용량이 무려 **30MB**에 육박했습니다.

"이게... 맞아?"

저는 제 눈을 의심했습니다. 게임도 아니고 단순한 블로그 페이지가 30MB라니! 만약 제 블로그가 대박이 나서 하루에 방문자가 10만 명씩 온다고 가정해 보세요. 이 용량이 그대로 트래픽으로 소모된다고 생각하니, 상상만 해도 등골이 오싹해졌습니다. 제 지갑이 순식간에 텅 비어버릴 것만 같았죠.

블로그는 콘텐츠가 핵심인데, 이렇게 무거워서야 되겠나 싶었습니다. 결론은 하나였습니다. **"최대한 가벼운 웹페이지를 만들 필요가 있다!"**

### 정적 웹사이트, 블로그의 황금률

가벼운 웹페이지를 만들기 위한 해답은 **'정적 웹사이트(Static Website)'**였습니다. 정적 웹사이트는 말 그대로 내용이 고정된 HTML 파일을 미리 만들어두고, 사용자가 요청할 때 그 파일을 그대로 보여주는 방식입니다.

정적 웹사이트의 장점은 명확했습니다.

- **미친듯한 속도:** 서버에서 복잡한 연산 없이 파일을 바로 전송하므로 로딩 속도가 찰나의 순간입니다.
- **완벽한 SEO:** 검색 엔진 크롤러가 HTML 파일을 완벽하게 읽을 수 있어, 검색 결과 노출에 매우 유리합니다. (블로그의 생명이죠!)
- **높은 보안성:** 데이터베이스나 서버 측 로직이 없어 해킹 위협이 거의 없습니다.

### 마크다운과 자동화, 개발자의 꿈을 이루다

또한, 저는 블로그 포스팅을 위해 복잡한 관리자 페이지에 접속하고 싶지 않았습니다. 제가 원하는 방식은 **마크다운(Markdown)** 파일로 글을 작성하고, 이 파일들을 깃허브(GitHub)에 '푸시(Push)'하는 것만으로 블로그에 자동으로 새 글이 올라가는 것이었습니다. 개발자에게 이보다 더 편한 워크플로우는 없죠!

### React와 Next.js, 구원의 기술 스택

저는 풀스택 개발자로 일하면서 **React**를 다뤄본 경험이 있었습니다. '내가 할 줄 아는 기술을 안 쓸 이유가 없지!'라는 생각으로 React로 눈을 돌렸습니다.

하지만 순수 React로만 블로그를 만들면 동적 웹사이트(CSR)가 되어, 초기 로딩 속도나 검색 엔진 최적화(SEO) 측면에서 불리하다는 것을 알고 있었습니다. 블로그는 검색 엔진 노출이 생명이니까요.

정적 웹사이트(SSG)를 만드는 방법을 찾아보니, **Next.js**를 이용하면 React 기반으로 매우 간단하게 정적 페이지를 만들 수 있다는 것을 알게 되었습니다.

### Next.js vs. 순수 React 전격 비교

Next.js와 순수 React로 블로그를 만들 때의 주요 차이점을 비교해 봤습니다.

| 항목                       | Next.js (프레임워크)     | 순수 React (라이브러리)      |
| -------------------------- | ------------------------ | ---------------------------- |
| **렌더링 방식**            | SSG (정적), SSR (서버)   | CSR (클라이언트)             |
| **SEO (검색 엔진 최적화)** | **매우 우수**            | 상대적으로 불리              |
| **초기 로딩 속도**         | **매우 빠름**            | 느릴 수 있음                 |
| **라우팅 (페이지 이동)**   | 파일 기반 자동 설정      | 라이브러리 설치 후 수동 설정 |
| **적합한 용도**            | 블로그, 쇼핑몰, 웹사이트 | 웹 애플리케이션, 대시보드    |

결론은 Next.js로 기울었습니다. 비록 Next.js를 직접 사용해 본 경험은 없었지만, 블로그를 만드는 수준이라면 충분히 할 수 있을 것 같았습니다. 웹 개발자의 자존심을 지킬 때였죠!
